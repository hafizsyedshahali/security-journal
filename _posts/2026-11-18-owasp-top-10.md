The **OWASP Top 10** is a list, published by the Open Worldwide Application Security Project, of the ten most important web application security risks. It's updated every few years from real-world data, and the latest version is **2025**. TryHackMe groups the ten into themed rooms, and I'll follow that grouping here.

A note on my notes: I wrote one category as "A06 Software or Data Integrity Failures". In the 2025 list that risk is actually **A08**. I've used the correct numbers below.

## Theme 1: IAAA failures (A01, A07, A09)

**IAAA** stands for Identification, Authentication, Authorisation and Accountability. These three risks are about failures in that chain.

### A01: Broken Access Control

**Access control** decides what a logged-in user is allowed to do. It's **broken** when those rules can be bypassed. The classic example is **IDOR (Insecure Direct Object Reference)**: a page uses `account?id=123`, and simply changing it to `id=124` shows someone else's account, because the server never checks that the record belongs to you. Access control jumped to the number one spot because it's so common and so damaging. The fix is to enforce permissions on the **server** for every request, and to deny by default.

### A07: Authentication Failures

**Authentication** is proving who you are. This covers weak points like allowing weak or common passwords, not limiting login attempts (which allows brute force), weak password recovery, and poor session management (such as session tokens that don't expire). Defences include strong password policies, rate limiting and lockouts, multi-factor authentication, and secure session handling.

### A09: Logging and Alerting Failures

If attacks aren't **logged** and nobody is **alerted**, breaches go unnoticed for months. This category is the one most directly about my future job. It fails when security events aren't recorded, logs lack detail, or alerts are never generated or never seen. Studies regularly show attackers spend a long time inside networks before being detected, and this is why. Good logging and alerting, with a SOC watching, is the fix.

## Theme 2: Design flaws (A02, A03, A06)

These are weaknesses baked into how a system is built or set up, rather than single coding bugs.

### A02: Security Misconfiguration

Software that's insecure because of how it's **configured**: default passwords left in place, unnecessary features switched on, detailed error messages shown to users, missing security headers, or cloud storage left open to the public. The fix is hardening: secure defaults, removing what you don't need, and checking configuration regularly.

### A03: Software Supply Chain Failures

Modern applications are built from many third-party components and libraries. A **supply chain failure** is when one of those trusted pieces is vulnerable or malicious, so you inherit its weakness. Real incidents have involved compromised libraries and build systems. Defences include tracking your dependencies (a software bill of materials), checking them for known vulnerabilities, and pinning trusted versions.

### A06: Insecure Design

A flaw in the **design** itself, not the implementation. Even perfectly written code can't fix a feature that was unsafe by concept, for example a password reset that relies on an easily guessed security question. The answer is to think about security during design: threat modelling and secure design patterns, before code is written.

## Theme 3: Insecure data handling (A04, A05, A08)

How an application protects and trusts data.

### A04: Cryptographic Failures

Failures in protecting data with **cryptography**: sending sensitive data without encryption, using broken algorithms like MD5 or DES, hard-coding keys, or storing passwords without proper hashing. This ties directly to the cryptography and hashing posts: use strong, current algorithms, protect keys, and encrypt sensitive data in transit and at rest.

### A05: Injection

**Injection** happens when untrusted input is treated as code. **SQL injection** (covered yesterday) is the best-known, but it also includes command injection and cross-site scripting (XSS), where input becomes script that runs in another user's browser. The fix is the same principle throughout: separate code from data, validate input, and use parameterised queries and output encoding.

### A08: Software or Data Integrity Failures

Trusting software or data without checking it hasn't been **tampered with**: installing updates without verifying their signature, loading code from an untrusted source, or deserialising data from an attacker. The defence is verifying integrity, for example checking digital signatures on updates, which connects back to the digital signatures from the cryptography post.

## A10: Mishandling of Exceptional Conditions

New in 2025. This covers errors and unexpected situations being handled badly: failing in an insecure way ("fail open" instead of "fail closed"), leaking information in error messages, or crashing in ways an attacker can use. The room notes didn't cover this one, but it completes the list.

## Why this matters for a SOC engineer

The OWASP Top 10 is a shared language. When a web alert fires or a scanner reports a finding, it's usually mapped to one of these categories. Knowing them helps a SOC understand what an alert really means, judge how serious it is, and explain it clearly to the people who have to fix it. A09 in particular is the SOC's own reason to exist.
